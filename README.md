# security-scan-kit

Trivy・Semgrep CE・Vuls・Prowlerで検査し、結果をDefectDojoに集めて、日本語の報告書を作るキットです。手動のリポジトリ一括検査では、依存脆弱性・コード・秘密情報・設定ミスを一緒に確認し、SBOMも保存できます。入口は http://127.0.0.1:18080/kit/ です。

## 起動のしかた

macOSで、Docker Desktop・Homebrew・uv・Goを用意し、Docker Desktopを起動してから実行します。

```sh
git clone https://github.com/bigzizi1240-debug/security-scan-kit.git ~/work/security-scan-kit
cd ~/work/security-scan-kit
bin/kit install
bin/kit up --open
```

- DefectDojoと画面が起動し、ブラウザで開きます（初回は数分かかります）。以後は `bin/kit up --open` で起動できます。
- デスクトップの起動アプリを作る場合は、上記の場所にcloneしてから `osacompile -o ~/Desktop/脆弱性スキャン.app launcher/脆弱性スキャン.applescript` を実行します。
- DefectDojo にログインします。ユーザー名は `admin` です。パスワードは `bin/kit password` でクリップボードにコピーします(45 秒後に消えます)。
- 左のメニューの **スキャンと報告書** が、このキットの画面(http://127.0.0.1:18080/kit/)です。

| タブ | できること |
|---|---|
| 検査する | 「リポジトリをまとめて検査」で依存・コード・秘密情報・設定とSBOMを検査する。既存のプリセット一括・個別検査・AI確認・仕分け・リスク受容も使える |
| 実行状況 | 実行中と過去の検査の状態・ログ・所要時間を見る。止める。取り込んだ DefectDojo の検査へ移る |
| リポジトリ結果 | 一括検査の結果と工程別の状態を確認する。顧客・重大度・種類・文字列で絞り込む。対象ファイル・修正版・固定ルールの説明を読み、SBOMと結果JSONを保存する |
| 報告書 | 顧客と、載せる指摘(大項目: すべて・①・②・③。小項目: すべて・直す・システムごとに決める・リスク受容)を選んで報告書(HTML・PDF・CSV)を作る。作った報告書を開く・保存する |
| ダッシュボード | 大項目(① 外部攻撃系統・② 横展開系統・③ 低可能性)ごとのページで、有効な指摘の件数と、重大度ごと・システムごとのグラフを見る。「詳細(小項目)を見る」で、小項目(直す・システムごとに決める・リスク受容)ごとの件数と重大度の内訳を見る。範囲ごとに DefectDojo の一覧を開く(0 件の範囲は除く)・PDF と CSV を保存する |
| 分類の設定 | システムごとの公開範囲(分類の前提)を直し、分類し直す |

DefectDojo の左のメニューの「スキャンと報告書」の下に、大項目(① 外部攻撃系統・② 横展開系統・③ 低可能性)があり、押すとダッシュボードのその大項目のページが開きます。大項目の下の「直す」「システムごとに決める」「リスク受容」は、そのページの詳細(その小項目)を開きます。上の「顧客」の欄で選んだ顧客の分で開きます(選んだ顧客はブラウザが覚え、ダッシュボードの顧客の欄と同じです。欄は DefectDojo の管理者にだけ出ます)。

検査は画面のサーバーとは別のプロセスで動くので、ブラウザを閉じても続きます。状態とログは `data/jobs/` に残ります。

## リポジトリをまとめて検査する

1. 「検査する」で「リポジトリをまとめて検査」を選びます。
2. 顧客と、Git cloneのフォルダ、cloneを並べたフォルダ、または `https://github.com/所有者/リポジトリ` を指定します。
3. 必要ならブランチを指定し、「まとめて検査する」を押します。
4. 「実行状況」で進行を確認し、「リポジトリ結果」で結果を開きます。「SBOMを保存」でCycloneDX JSONをダウンロードできます。

検査するのはoriginの指定ブランチ（省略時は既定）の一つのcommitです。各検査は同じコードを使います。手元の未コミット変更は含めず、作業ツリーと既存refも変更しません。originに接続できず手元のrefを使った場合は、最新か未確認であることを結果に表示します。GitHubの非公開リポジトリは、対話なしで取得できる既存のGit認証が必要です。

コード本文・秘密値・SASTの動的メッセージを結果に残さず、ルールと場所、部品名・版、重大度を保存します。Semgrepは固定digestのコンテナをネットワークなしで実行し、同梱MITルールだけを使います。ルールの出典と範囲は [rules/README.md](rules/README.md) を参照してください。初回導入は `bin/kit install` で固定イメージも取得します。

失敗・未実施・解析エラー・中断は検出0件と区別します。一工程が失敗しても残りの検査と結果保存を続け、DefectDojoへの登録に失敗しても「リポジトリ結果」で保存済みの指摘を確認できます。新しい一括検査の取込では過去の指摘を自動で閉じません。既存の単独検査・報告書の対応履歴は維持します。

SBOMには、脆弱性がないと判定された部品も含めて保存します。ただしソースリポジトリで検出できた部品の一覧であり、配備中の実体との一致や、手置きライブラリ・GAS・CDN依存等の網羅性は未確認です。link・submoduleの実体は対象外として表示します。通常ファイルはGit属性の除外・置換に依存せず取得し、安全な書出し上限は50,000ファイル・単一16MiB・合計256MiBです。SASTにはさらにファイルサイズ・言語・固定ルールの解析範囲があります。

これは静的な検査結果です。指摘0件や工程の完了は、Webの安全性・悪用成立の検証やZAPによる総合診断の完了を意味しません。追加した一括検査では、リポジトリ内のbuild/install scriptやAI分析を実行しません。

CLIからも使えます。

```sh
bin/kit repository-scan /path/to/clone --client DEMO
bin/kit repository-scan https://github.com/owner/repo --client DEMO --branch main
# 対応履歴へ取り込まず、検査結果とSBOMだけを保存する場合
bin/kit repository-scan /path/to/clone --client DEMO --no-import
```

## 検査の種類

| 画面の選択 | 中身 |
|---|---|
| リポジトリをまとめて検査 | 一つのcommitを取得し、Trivy・SAST・SBOMを実行。工程別の完了状態と統合結果を保存する |
| Trivy:Git の clone | clone(または clone を並べたフォルダ)を、origin の既定(または指定)のブランチの最新の状態で検査する。`git ls-remote` で先端を調べ、そのコミットだけを取り寄せて書き出すので、手元の作業ツリーと ref は変えない。origin に届かなければ手元の ref で検査し、ログに「古い可能性あり」と出す |
| Trivy:フォルダ | フォルダを今のファイルのまま検査する |
| Trivy:イメージ・URL | コンテナイメージ(非公開なら先に `docker login`)、リポジトリの URL |
| Vuls | 設定ファイル(見本は `vuls/config.example.toml`)のサーバーを SSH で検査する。初回の報告で脆弱性 DB(圧縮 283MB、展開後 **約 13GB**)を `data/vuls-db/` に取る。macOS の検査は誤検知が多い |
| Prowler | AWS(`--profile`)・GCP(ADC)・Azure・GitHub の組織・Kubernetes・Microsoft 365・IaC。GitHub は gh のログインのトークンを、環境変数で Prowler だけに渡す |

DefectDojoでは「顧客(組織)/ 対象システム / 案件 / 検査」の順に並びます。既存の単独検査は同じ案件・検査へ再取り込みし、消えた指摘を「対応済み」にします。新しいリポジトリ一括検査は検査範囲の違いや部分失敗で誤って解消扱いにしないよう、自動で閉じません。Gitの検査にはコミットとブランチを記録します。

## 分類(①〜③)

指摘を、攻撃者からの届き方で 3 つ(大項目)に分け、DefectDojo の指摘にタグ(`①外部攻撃系統`・`②横展開系統`・`③低可能性`)を付けます。根拠が足りないものには `分類を要確認` も付けます(件数はダッシュボードの各ページに出ます。押すと「分類の設定」)。取り込みのたびに自動で分類し、規則は `lib/classify.py` にあります。機械のルールによる推定で、実際に悪用できるかまでは確かめていません。

| 分類 | 意味 | 主な判断の材料 |
|---|---|---|
| ① 外部攻撃系統 | 外部の攻撃者の入力が、そのまま届く可能性がある | 外部に公開しているシステムの依存で、CVSS の攻撃元がネットワーク(ログインが要る画面なら、ログイン前に届くもの)。外部への公開に関わる設定(Prowler の internet-exposed など)。公開リポジトリやブラウザに配られるファイルの秘密情報 |
| ② 横展開系統 | フィッシングなどで中に入った攻撃者や、盗まれたアカウントが悪用できる | 内部だけのシステムの依存。ログインが要る画面の、ログイン後の依存。攻撃元がローカル・隣接ネットワークのもの。権限・アカウント・変更の管理の設定(MFA・ブランチ保護など)。非公開リポジトリの秘密情報 |
| ③ 低可能性 | ①②の経路が見当たらない | テスト・文書・配備していない場所の依存。物理的な接触が要るもの。堅牢化の推奨。公開してよい種類の鍵。権限が足りず確かめられなかったチェック |

2026-10-30 に「③ 可能性が低い」を「③ 低可能性」に、2026-10-31 に「① 外部から直接」を「① 外部攻撃系統」に、「② 横展開」を「② 横展開系統」に改めました。前のタグは、分類し直す(取り込み・「分類の設定」の保存・`bin/kit classify`)と今のタグに付け替わります(誤検知・重複・リスク受容にした指摘のタグも付け替えます)。

依存の脆弱性を ① から外すのは、外から届かないという根拠があるものだけです(システムの公開範囲の設定、配備していない場所、CVSS の攻撃元がネットワーク以外、AI の確認の「影響なし」)。CVSS のほかの条件(利用者の操作が要る・攻撃の条件が難しい)やブラウザの画面かどうかだけでは外しません。ライブラリの CVSS は一般的な使い方での採点で、外から狙える XSS なども含むためです。

### 二重の数え(重複)をまとめる

同じフォルダにロックファイルが 2 つ(`package-lock.json` と `yarn.lock` など)あると、Trivy は同じ部品の同じ脆弱性をロックファイルごとに出します。同じアプリの同じ問題なので、取り込みと分類し直しのたびに、分類の前に 1 件だけ残し、残りは DefectDojo の「重複」にします(規則は `lib/dedupe.py`)。重複は有効な指摘に数えません。

- まとめるのは、同じ検査・同じフォルダ・同じ公開範囲の、JavaScript と Python のロックファイル(`package-lock.json`・`yarn.lock`・`pnpm-lock.yaml`・`Pipfile.lock`・`requirements.txt` など。一覧は `dedupe.LOCKFILES`)に出た、同じ部品・同じ版・同じ脆弱性の ID の指摘です。イメージの中のプログラム、秘密情報・設定の指摘、ID のない指摘はまとめません。
- 残すのは、AI の確認で「影響あり」 → 「要確認」 → ID の小さいもの、の順です。人が仕分けを変えた指摘と、すでに重複を持つ指摘は、重複にしません(DefectDojo は、重複を持つ指摘を重複にすると、有効なまま残してしまうため)。
- 報告書と CSV の場所には、まとめた側のロックファイルも並べます(どのファイルも直せるように)。
- 残した方が直って閉じたのに、重複の方がまだ残っている(片方のロックファイルだけ版を上げたなど)ときは、重複を有効に戻します。残した方が誤検知・範囲外・リスク受容なら、同じ判断が当てはまるので重複のままです。まとめたあとに「分類の設定」で片方だけ公開範囲が変わったとき(ファイル単位のパスの例外など)も戻します(残した方が誤検知・範囲外なら、コードについての判断なので重複のまま)。
- まとめに失敗しても、分類と仕分けは続けます(二重の数えが残るだけ。`bin/kit classify` でやり直せます)。

判断の要は、システム(DefectDojo の製品)ごとの公開範囲で、`data/<顧客名>/systems.json` に置き、画面の「分類の設定」で直します。

- 公開範囲は 5 種類です: `external`(外部に公開・誰でも入力を送れる)、`external-auth`(外部に公開・組織のログインが要る)、`internal`(内部だけ)、`none`(配備していない)、`unknown`(未設定)。
- 未設定のシステムは外部に公開とみなし、「分類を要確認」を付けます。新しい顧客は、最初にここを埋めてください。
- 1 つのリポジトリに性質の違うものが同居するときは、パスの例外を「パス=公開範囲」で書きます(例: `backend/lambda/ai_report/=internal`)。
- テスト・文書・見本の場所(`test/`・`docs/`・`examples/` など)は、自動で「配備していない」とみなします。
- DefectDojo には NVD の CVSS v3 しか入らないので、ベクターがない依存の指摘は、Trivy の元の結果(GHSA・Red Hat などの CVSS)で補います。Prowler の指摘も、元の結果のチェックの ID と分類で判断します(元の結果の場所は `data/<顧客名>/tests.json`)。
- 公開範囲は、検査の許可範囲と実際の配備構成を確認して設定してください。公開版には個別組織の設定を含めていません。

## AI で再現性を確かめる

依存の脆弱性が本番で再現するか(影響の条件を満たすか)を、Claude Code に確かめさせます。画面の「検査する」で「AI で再現性を確かめる」を選び、顧客と範囲(① の緊急・① の緊急・高・依存の脆弱性すべて)を選びます。ターミナルでは `bin/kit ai-review --client DEMO --scope critical` です。

リポジトリ一括検査の指摘は、検査IDに保存したcloneとcommitを使います。過去の指摘や複数の版が混在して対応を確かめられない場合、AI確認を保留します。GitHub URLの検査で使った一時cloneは残さないため、あとからAI確認する場合は手元のcloneで再検査してください。

- 単位は「対象システム × 部品」です。検査したときと同じコミットのソースを `/private/tmp` の一時フォルダに書き出し、終わったら消します。
- 書き出したソースでは、Trivy が見つけた秘密情報らしき行と `.env` の値を伏せ、AI への指示になりうるファイル(`CLAUDE.md`・`.claude`・`.mcp.json`)を消します。
- Claude Code は副業の設定(`~/.claude-xany`。環境変数 `KIT_AI_CONFIG_DIR` で変えられる)で動かします。ユーザーの設定(読めるフォルダの追加など)・MCP・会話の保存は使いません。道具は読み取りだけ(Read・Grep・Glob)で、作業フォルダの外は読めません。お客様のソースは Anthropic に送られます。
- 判定は「影響あり・影響なし・要確認」です。DefectDojo のタグ(`ai判定-影響あり` など)と、理由・根拠(ファイルと行)・再現の手順の案を書いたメモに残します。手元の記録は `data/<顧客名>/ai-review.json` です。
- 根拠を示せた「影響なし」は、誤検知(False Positive)にします。一覧と報告書から外れ、次の取り込みでも戻りません。報告書の 4 章に、その報告書の範囲(分類)で今も誤検知のものの件数が載ります。判定が間違っていたら、DefectDojo でその指摘の誤検知を外してください。
- 報告書の 3 章の「AI の確認」に、判定と理由が載ります。同じ指摘が複数のシステムにあるときは、システムごとに並べます。
- 判定を確かめた補足(抜き取りの確認)は、`ai-review.json` のその指摘の `review`(`by`・`at`・`text`)に入れると、報告書の「AI の確認」の後ろに出ます。DefectDojo には同じ文をメモとして足します。
- 確かめるのは、まだ判定のない指摘だけです。確かめられなかった単位は、もう一度実行すると確かめます。
- 判定ごとの一覧は、DefectDojo の検出事項の一覧をタグ(`ai判定-影響あり` など)で絞ると見られます。
- AI の判定は、コードと設定を読んだうえでの推定です。実際に攻撃を試したものではありません。
- AI の確認が終わると、判定を反映して仕分けし直します(①② の「影響あり」は「直す」。③ はすべてリスク受容のまま)。

## 仕分け(直すか、受け入れるか)

有効な指摘を、次の 3 つ(小項目)に仕分けて、DefectDojo のタグ(`仕分け-直す` など)を付けます。取り込み・分類し直し・AI の確認のたびに、自動で仕分けます。規則は `lib/triage.py` にあります。機械のルールによる推定です。

| 仕分け | 主な条件 |
|---|---|
| 直す | 秘密情報。CISA KEV に載っている(実際の悪用を確認)。AI の確認で「影響あり」。EPSS が 10% 以上(30 日以内に悪用される見込み)。同じ系列(メジャー版。0.x はマイナー版)の版上げで直る依存。GitHub の設定でまとめて直せるもの(既定ブランチの保護、強制 push と削除の禁止、組織のリポジトリの作成・削除の制限、放置したリポジトリ) |
| システムごとに決める | 系列をまたぐ版上げが要る依存。直した版がない依存。規則のないもの(クラウドの設定、サーバーのパッケージなど) |
| リスク受容 | ③ 低可能性のすべて。体制に合わせて決める GitHub の運用ルール(署名、承認の人数、CODEOWNERS、状態チェックなど)。コンテナを root で動かす設定と、記録(ログ)の設定(Trivy の設定ミス) |

- ③ 低可能性は、すべて「リスク受容」にします(まとまりは「低可能性」)。CISA KEV・EPSS・AI の「影響あり」があっても変えません。人が変えた仕分けは残ります。
- 仕分けのタグが 2 つ以上ある指摘(人が足したなど)は、急ぐ方(直す → システムごとに決める → リスク受容)に数えます。ダッシュボード・報告書・リスク受容の登録とも同じです。
- 「直す」のうち急ぐもの(秘密情報・KEV・AI の影響あり・EPSS 10% 以上)は、理由(「CISA KEV に載っている」など)と DefectDojo の EPSS・KEV の欄で分かります。
- 直す順は、悪用の証拠(CISA KEV に載っている・EPSS 10% 以上)があるものと秘密情報(漏れた鍵はそのまま使われる。③ の公開してよい種類の鍵は除く) → AI の確認で「影響あり」のもの → そのほか、です。報告書の各節はこの順(その中は重大度の順)に並び、一覧と詳細に「悪用の証拠」「秘密情報」「AI で影響あり」の印が付きます。CSV の「優先」の列(例: `1: 悪用の証拠`・`3: そのほか`)も同じです。
- 「システムごとに決める」は、直すか受け入れるかを機械で決められないものです(大きな版上げで改修が要る、直した版がない、など)。判断はシステム単位でまとまります。
- 2026-10-30 に 4 区分(すぐ直す・まとめて直す・システムごとに決める・受け入れ候補)から 3 区分にしました。前のタグは、次の仕分けで今のタグに付け替わります(人が変えた仕分けも、その意味のまま引き継ぎます)。
- 人が DefectDojo で仕分けのタグを別のものに変えると「手動」になり、キットは上書きしません。仕分けのタグを外すと、自動の仕分けに戻ります。タグを変えたあと仕分けし直すまでは、報告書に前の理由を載せません。
- 仕分けの理由は `data/<顧客名>/triage.json` に残り、報告書の詳細に載ります。
- EPSS と CISA KEV は、一覧をまるごと取って手元で突き合わせます(CVE ごとに問い合わせないので、顧客の CVE の一覧は外に出ません)。`data/intel/` に置き、24 時間は取り直しません。取れないときは前の一覧を使います(報告書の 4 章に、使った版が載ります)。値は DefectDojo の指摘の EPSS・KEV の欄にも入ります。
- 画面の「検査する」の「仕分けし直す」(ターミナルでは `bin/kit triage --client DEMO --refresh`)で、一覧を取り直して仕分けし直せます。
- DefectDojo の左のメニューの大項目の下の「直す」などから、ダッシュボードのその小項目を開けます。そこから DefectDojo の一覧(大項目と小項目の両方のタグで絞る)・PDF・CSV へ進めます。

## リスク受容

今の仕分けが「リスク受容」の有効な指摘を、DefectDojo のリスク受容としてまとめて登録できます。画面の「検査する」の「リスク受容を登録する」で、顧客・対象システム・大項目(すべて・①・②・③)・受け入れた人・期限(90・180・365 日)を選びます。ダッシュボードのリスク受容のカードの「登録へ」からは、顧客と大項目を選んだ状態で移れます。先に件数の見込みが出るので、確かめてから登録します。確かめたあとに件数が変わっていたら(その間に仕分けし直したなど)、登録しません。ターミナルでは `bin/kit accept-risk --client DEMO --by "受け入れた人" [--tier 3] [--dry-run] [--expect 件数]` です。プリセットにはできません。

- DefectDojo の決まりで、リスク受容は案件ごとに作ります。キットは「案件 × 理由のまとまり」(例: GitHub の運用ルール)ごとに 1 つ作ります。
- 受け入れた指摘は DefectDojo で有効でなくなり、一覧と報告書から外れます(報告書の 4 章に件数が載ります)。取り込み直しても戻りません。
- 期限が来ると、指摘は有効に戻ります(「期限が来たら、指摘を有効に戻す」を外したときは戻りません)。
- 取り消しや期限の変更は、DefectDojo の案件の画面(リスク受容)で行います。
- 対象システムで「リスク受容(full)」が無効なら、その分は飛ばします。

## プリセット

画面の「検査する」に並ぶボタンは `data/targets.toml` に書きます。認証情報などの準備が足りないものは、ボタンの代わりに理由が出ます。

```toml
[[preset]]
name = "表示名"
note = "説明(省略可)"
client = "顧客名"
product = "対象システム名"    # 省略時は顧客名(Git はリポジトリ名)
tool = "prowler"              # trivy / vuls / prowler
provider = "aws"              # prowler のとき
args = ["--profile", "読み取り用のプロファイル"]
# trivy のとき: kind = "git" / "fs" / "image" / "repo"、target = "パスや名前"、branch = "ブランチ"(省略可)
# vuls のとき:  config = "設定ファイルのフルパス"
```

公開版にはプリセットを含めていません。許可された対象だけを `data/targets.toml` に追加してください。

- **GCP** を使うには、ターミナルで一度 `gcloud auth application-default login` を実行します(ブラウザでのログイン)。
  - 検査には、ADC のアカウントに閲覧者(roles/viewer)とセキュリティ審査担当者(roles/iam.securityReviewer)の権限が要ります。
  - 権限が足りないと、Prowler は何も検査できないまま「指摘なし」で終わります。そこでキットは、検査の前に権限を確かめ、足りなければ「範囲外」として検査しません。
  - Prowler の GCP には Cloud Run のチェックがありません。
- **AWS** を使うには、AWS CLI を入れて(`brew install awscli`)、読み取りの権限のプロファイル `example-readonly` を作ります(`aws configure sso`)。権限は `SecurityAudit` と `ViewOnlyAccess` で足ります。

### 今の権限で検査できる範囲

権限や認証情報が足りないものは、失敗にせず範囲外として扱います。報告書の 4 章「検査の範囲」に、検査したもの・検査しなかった対象・判定できなかった項目が載ります。画面のダッシュボードにも出ます。

- **一括検査**は、準備が足りないプリセット(認証情報がない)と、今の権限では検査できないもの(GCP の読み取りの権限がないなど)を飛ばして、次へ進みます。1 つだけ実行したときは、実行状況が「範囲外」になります。
- **GitHub**: Prowler は、管理者でないと読めない設定を「無効」とみなして不合格にします。そこでキットは、取り込む前に GitHub の API で今のトークンが読めるものを確かめ、次の結果を指摘から外します。外したものは、結果のフォルダの `out-of-scope.json` に残します。
  - secret scanning の設定を読めないリポジトリの「secret scanning が無効」
  - 既定のブランチが保護されているのに保護の中身を読めないリポジトリの、ブランチの保護の各項目
  - Prowler が「権限が足りず確かめられない」(MANUAL)とした項目
  - 空のリポジトリ(ブランチがない)の、ブランチの保護と CODEOWNERS
- Prowler は、読めない設定のチェックを、結果を出さずに飛ばすこともあります(組織の 2 段階認証の必須・既定の権限、Actions の権限、リリースの書き換え防止など)。キットは結果が出なかった(チェック, 組織かリポジトリ)も数えて、「判定できなかった項目」に載せます。GitHub Actions のワークフローの検査は、zizmor が入っていないと実行されないので、同じく載せます。`--checks`・`--status` などでチェックや結果を絞ったときは、これは数えません。
- 保護のないブランチの不合格や「Dependabot が無効」などは、GitHub が実際に返した値なので、そのまま指摘にします。
- ルールセットの例外(バイパスできる人)も、管理者でないと読めません。そのため「管理者にも保護を適用」の合格は、確かめられていない場合があります。
- 権限が減って判定できなくなった指摘は、次の取り込みで DefectDojo では「対応済み」として閉じられます(報告書では「判定できなかった項目」に載る)。

## 報告書

`data/<顧客名>/reports/` に HTML・PDF(Chrome のヘッドレス印刷)・CSV ができます。大項目(①・②・③)と小項目(直す・システムごとに決める・リスク受容)を選ぶと、その範囲の指摘だけの報告書になります(ファイル名の末尾が `-tier1-fix` など。ターミナルでは `bin/kit report --client DEMO --tier 1 --triage fix`)。ダッシュボードの「PDF」「CSV」は、その範囲の報告書を作って保存します。保存するときの名前は `DEMO_脆弱性診断_①外部攻撃系統_直す_20261030-2007.pdf` のようになります(作った報告書は「報告書」のタブに残ります)。

中身は、DefectDojo で「有効」の指摘の概要・一覧(同じ CVE などはまとめる)・詳細(緊急・高。分類の理由つき)と、検査の範囲(検査したもの・検査しなかった対象・判定できなかった項目)と注意、分類の基準です。概要に大項目・小項目ごとの件数が載り、一覧と詳細は「① 外部攻撃系統 › 直す」のような節に分かれ、各節の中は直す順(悪用の証拠・秘密情報 → AI の確認で影響あり → そのほか)に並びます。詳細には仕分けの理由と悪用の見込み(EPSS・CISA KEV)、最後に分類と仕分けの基準が載ります。CSV は 1 行 1 指摘で、先頭の列が大項目・小項目・優先(直す順)・仕分けの理由です(Excel で開けるよう UTF-8 の BOM 付き。数式として動かないよう、`=` などで始まる値には頭に `'` を付けます)。誤検知は DefectDojo で False Positive にすると報告書から外れます。

## データと通信の扱い

- 検査の結果・報告書・ログは `data/`(権限 700。git 管理外)と DefectDojo の Docker ボリュームにだけ置きます。Mac の FileVault を有効にしておいてください。
- **秘密情報の値は残しません。** Trivy が伏せ字にするのは、規則に一致した部分だけです(同じ行の残りは平文で出る)。キットは取り込む前に、結果から値を含む欄(Match・Code)を消し、場所(ファイルと行)だけを残します。
- Git の検査で書き出したソースの写しは、検査のあとすぐ消します(結果の JSON だけ残す)。
- 外から届くのは 127.0.0.1:18080(入口)だけです。画面のサーバーは 127.0.0.1:18081 で待ち受け、入口が付ける合言葉(キーチェーンの `KIT_GATEWAY_TOKEN`)のない要求を断ります。検査を始めるなどの書き込みは、この画面から送られたもの(Origin と専用のヘッダー)だけを受けます。
- 報告書の HTML は sandbox(DefectDojo から切り離した状態)で開きます。
- DefectDojo の秘密鍵・DB のパスワード・管理者のパスワードと入口の合言葉は、初回の起動で作り、キーチェーン(サービス名 `security-scan-kit`)に置きます。画面でパスワードを変えた場合は、キーチェーンの `DD_ADMIN_PASSWORD` も同じ値にしてください。
- DefectDojo のイメージは Docker Hub から取ります(upstream の既定のレジストリは、取得ごとに IP などを記録する)。画面の宣伝文の取得(storage.googleapis.com)は止めています。
- キットから DefectDojo への通信は、OS や環境変数のプロキシ(Burp など)を通しません。
- 外部への通信: イメージの取得、Trivy と Vuls の DB の取得(mirror.gcr.io・ghcr.io)、Git の検査での origin への接続、Prowler の新版の確認、検査の対象そのもの(GitHub の検査では、読める設定の確認に api.github.com も使う)、仕分けに使う EPSS(epss.empiricalsecurity.com)と CISA KEV(www.cisa.gov)の一覧の取得(一覧をまるごと取る。ふだんは 1 日 1 回まで、「仕分けし直す」ではそのつど。顧客の情報は送らない)。AI の確認では、お客様のソースを Claude Code(Anthropic)に送る。
- 第三者(顧客など)の環境を検査するときは、事前に許可を得てください。

## Trivy の注意

Trivy は 2026-03 にサプライチェーン侵害を受けています(CVE-2026-33634、GHSA-69fq-xp46-6x23)。キットは侵害された版(0.69.4〜0.69.6)では検査を止めます。更新は `brew upgrade trivy` で行います。

## コマンド

画面と同じことを、ターミナルからもできます。

```sh
bin/kit up [--open]          # 起動(画面のサーバーの入れ替えも)  /  bin/kit down で停止
bin/kit trivy git ~/work/example-sources --client DEMO
bin/kit vuls --config data/顧客A/vuls-config.toml --client 顧客A
bin/kit prowler github --client DEMO --product "GitHub example-org" -- --organization example-org
bin/kit scan-all --client DEMO  # 顧客のプリセットをすべて検査する(一括検査)
bin/kit classify --client DEMO  # 公開範囲を直したあと、分類し直す(仕分けもし直す)
bin/kit triage --client DEMO [--refresh]  # 仕分けし直す(--refresh で EPSS・CISA KEV を取り直す)
bin/kit accept-risk --client DEMO --by "受け入れた人" [--product 対象システム] [--days 180] [--dry-run] [--expect 件数]
bin/kit report --client DEMO [--tier 1] [--engagement "診断 2026-10"] [--open]
bin/kit doctor               # ツールの版、DefectDojo・画面・認証情報の状態
bin/kit password             # 管理者のパスワードをコピー
bin/kit logs                 # DefectDojo と入口のログ(画面のサーバーは data/web.log)
```

## 更新

- **Trivy**: `brew upgrade trivy`
- **Vuls・Prowler**: `lib/kit.py` の `VULS_VERSION`・`PROWLER_VERSION` を変えて `bin/kit install`
- **DefectDojo**:
  1. `defectdojo/docker-compose.yml` を新しい版の upstream に差し替える。
  2. `defectdojo/docker-compose.override.yml` のイメージの版と digest、`lib/kit.py` の `DD_VERSION` を変える。
  3. `bin/kit install` → `bin/kit down` → `bin/kit up`(データベースの移行は自動)。
  4. 左のメニューへの差し込みは、DefectDojo の HTML の `<!-- Products -->` を目印にしている(`defectdojo/gateway/default.conf.template`。顧客の欄は `web/sidebar.js`)。版を上げて出なくなったら、ここを直す。入口の設定を変えたら `docker restart security-scan-kit-gateway-1` で読み直す。読み直す前に、同じイメージで設定を確かめる: `docker run --rm -v "$PWD/defectdojo/gateway:/etc/nginx/templates:ro" -e KIT_GATEWAY_TOKEN=dummy -e KIT_WEB_PORT=18081 --add-host host.docker.internal:host-gateway "$(docker inspect security-scan-kit-gateway-1 --format '{{.Config.Image}}')" nginx -t`。nginx は 1 つの値を 4096 バイトまでしか読めない(超えると入口が起動しない)ので、差し込む HTML は変数(`$kit_menu_*`)に分けてある
- **画面のコード**(`lib/`・`web/`)を変えたら `bin/kit up` で入れ替わります。
- DefectDojo の設定「filter_string_matching」(一覧を文字列で絞る)は無効のままにします。有効にすると、ダッシュボードから開く一覧の絞り込み(大項目と小項目の両方のタグ `tags_and`、急ぐ小項目を除く `not_tags`)が効きません。

## 作り直す(すべてのデータを消す)

```sh
bin/kit down
docker compose -p security-scan-kit down    # コンテナを消す
docker volume rm security-scan-kit_defectdojo_postgres security-scan-kit_defectdojo_media security-scan-kit_defectdojo_redis
for n in DD_SECRET_KEY DD_CREDENTIAL_AES_256_KEY DD_DATABASE_PASSWORD DD_ADMIN_PASSWORD KIT_GATEWAY_TOKEN; do
  security delete-generic-password -s security-scan-kit -a "$n"
done
bin/kit up
```
